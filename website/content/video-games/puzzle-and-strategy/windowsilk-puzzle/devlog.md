# Devlog: Windowsilk (Puzzle)

So, I made the game **Windowsilk** for the GitHub Game Off.

That version was a local multiplayer party-esque game. You move in realtime, the web can have *any* configuration you want (no grid, no fixed rotations, no fixed line lengths) and you can add new lines however you want (by jumping).

All good fun, but as I created the game, I realized many of the ideas I had would (perhaps) better suit a **puzzle game**. So I'm going to try and create that little game now.

## The rules

**Objective:** Become maximum size = reach 10 points (or another convenient number)

**Input:** click to move your spider to a node, or use arrow keys/joystick to indicate direction.

**Move:** so, yes, the only *move/turn* you can do is literally *moving*. This makes it really simple. And because it all happens on a spider web, it's quite intuitive how it works (and where you can or can't move).

**Board:** a rectangular grid. I thought about making it dynamic as well, but that's just not a good idea for a *puzzle* game. I also though about different grids, but because of some huge challenges in this project (I will talk about soon), I decided to stick to the easiest one to implement.

## The mechanics

**Rules:** but what are the actual rules of the puzzle? An altered, simplified version of the real game:

-   All entities (including player) have points.

-   If you meet another entity with fewer points, you eat it, and get their points.

This is the basic idea. The first few puzzles should just be: find the quickest route to gather the points you need (by eating bugs)

After 5-10 puzzles, however, this will become quite boring.

We go to phase 2, so to speak: **jumping**

-   Players can jump to unconnected nodes in the web. This creates a new edge, but you must pay a point.

-   Flying bugs appear. Obviously, you can only eat them by jumping and catching them mid-air.

Once that turns stale, we go to phase 3: **specialties**

-   Bugs can have their own *specialty*. If you eat them, you get that specialty. (Which might be something like "jumping is free" or "can't eat anyone this turn".)

-   Specialties either wear out after 1 turn, are permanent, or can be reset when walking over a certain point. (Not sure which one is best.)

Then we get to the real fun in phase 4: **moving entities.** Instead of bugs just sitting still, waiting for you, they'll move around.

-   There should be some extremely simple rule to determine which way they go, and in what order.

Which leads to phase 5: **trails**

-   From now on, you leave a trail. Edges you create are *yours*. This means that any entity walking on it, will get stuck and become free to eat.

-   Some bugs also leave a trail. When they walk over something, they change the type of edge to their specialty.

I should be able to copy *most* bugs (and their trail/specialty, which is the same thing 99% of the time) from the original game to the puzzle game. And then I'll call it quits, because I don't want this project to become too large.

## Generating puzzles

Earlier this year, I've created a puzzle game where all puzzles were *generated by the computer*. (I also did a similar thing a year before that, but that game hasn't been released yet, partly because I didn't know what I was doing yet.)

This is *amazing*. (Endless puzzles, which I can play myself as well, unexpected mechanics that appear, no need to create them by hand, etcetera.)

It's also *incredibly hard*. You need to

-   Explain to the computer how to generate a random board, try all possible moves, and return the solution if there is one.

-   Make this *fast enough* that you don't need to wait one hour for a single puzzle try.

-   And make this *smart enough* to actually yield good, engaging, simple, fun puzzles.

There's absolutely no guarantee that a computer will find anything useful, especially not if it's just trying completely random stuff. The number of possible states *also* balloons really quickly, which I'll explain in a bit.

In the end, though, I decided to go the computer-generated puzzle route again. Why? Because I've wanted to learn the programming language **Rust** for quite some time now. It's supposed to be fast, fun (once you understand it a bit), *and* encourages good programming patterns and practices. Being frustrated with some of my older tools (especially **Java**, used for the previous puzzle generation), I wanted to switch.

So I embarked on a journey to rewrite my old simulation code (well, the parts that are applicable here) in Rust, to learn the language. And then put the new code on top, and use that to generate random puzzles.

### Why do I need speed?

After a day of fiddling with Rust, I got a system working that:

-   Creates a random board. (Points in grid, some randomly connected with an Edge, Player somewhere.)

-   Then tries *all possible moves* (one at a time), doing and undoing as necessary.

-   Up until a maximum number of moves I can configure myself.

Notice that there is **no logic at all yet**. The "do" and "undo" functions, which will be crucial and complex once the project grows, are empty now.

Just checking all moves for a puzzle with 8 maximum moves, leads to **20 million moves** to check. (The spider can go in 8 directions as well: horizontal, vertical, diagonal.) Even without any logic, this takes a few seconds to race through.

Believe me, the first time I tried random puzzle generation I wrote it in my actual game engine ... and it took almost an *hour* to go through that many states, with barely any logic implement.

So yes, speed is something I want, even if it means struggling through the unique ways of Rust for a few days (or weeks).

### Surely we can speed this up other ways?

Yes! Yes we can!

**Firstly,** because there's no logic, it literally tries *all moves*. But ... if there isn't an edge in that direction, you can't walk there anyways. So we can ignore those moves. Similarly, if you have no points for a jump, no need to try that.

Implementing this reduces the states to check to **90000** (with jumping disabled). And **XX TO DO** with jumping enabled. (On a 3x3 board with 8 options per move.)

**Secondly,** we can keep the max moves small. My experience with the previous game told me that *having a huge number of possible moves/states* is actually *detrimental to the puzzle*. It's overwhelming. It means there are too many paths to take and no clear way forward for the player.

As such, I learned that capping moves at 5-8 is actually great. Additionally, I can *count* how many states we already tried, and if it goes above something like 1 million ... I abort the mission and just try again with a new puzzle.

(Of course, it also helps massively to keep the *level size* small. The more points and edges you add, the more you need to store in memory, and the more freedom there is to move for the player.)

**Thirdly,** we do a "depth-first search". (It means we try a single solution completely, before trying the next. "Breadth-first" would mean we first try all solutions with 1 move, then all solutions with 2 moves, etcetera.)

This has pros and cons. The pro is that our program requires basically no memory, making it really fast in general. (We only save *one board state* at a time.) Another pro is that any puzzle with a *long solution* will find it sooner.

The con is that puzzles with *short solutions* won't be discarded as quickly. Even if a puzzle has a simple solution of 3 steps ... it might take us 50000 tries of very long solutions to finally try *that* 3-step solution.

That's fine, though, as I don't see puzzles with \<4 moves being an actual puzzle. We want the slightly longer ones.

**Fourthly**, we can use a "progress heuristic". If we've done 6 moves (out of our total 8), and the player is *still* only at 0 points ... there's no real chance of winning this one, eh? Abort, try a new solution.

Applying this heuristic leads to impreciseness: puzzles that actually *have* a solution might be discarded. But it's highly unlikely. And in return, we can skip *loads* of solutions after only a few moves.

**Lastly,** we can use the game's mechanics to lower the options. Again, this not only works for the simulation, it's also a good puzzle principle as well!

If all mechanics *add* more options to the game, it becomes overwhelming and too complex. Instead, you want a puzzle with a few clear restrictions that force the player to think "how do I get *around* these handful of restrictions?"

For example, I can add a bug that disallows jumping (once eaten). Once the player eats them, *they will only have 1 or 2 possible moves on all subsequent turns* (because jumping isn't an option). This, again, skips many moves.

## Some things about Rust

### First experiences

The main thing about rust is that **every piece of data has exactly one owner**. This is both its unique feature/philosophy, as well as how it's able to manage memory and be so extremely fast (without requiring a so-called "garbage collector" or other tricks).

At first, this might not sound like much. Like: "yeah, fine, I'll just make sure I give every piece of data to one thing at a time"

But when you start to write an actual program, you soon realize the deep implications this has. And how all the ways you used to code suddenly don't work anymore.

On my first try, I did the usual stuff. Created a Point struct ( = class), an Edge, an Entity, etcetera. Then I created a big Board struct to hold all of that, generate a random board, and then place the player entity.

I was happy with myself, and the compiler was happy for a while ... but then the trouble started. The simplest things weren't possible, because I was breaking the rules of Rust. It sometimes took me an hour to figure out just *why* something was not allowed, as I was certain I wasn't handing out data to different owners.

Here's an example:

-   When generating the board, I have to generate the *edges* between all points.

-   So, I loop through the points, and for each neighbor of a point, I add an edge. (Between the current point and that neighbor.)

Nope. Not possible.

Why not?

-   Anytime I add an edge, I need to inform the points it attaches to. ("Hey, you just got this extra edge!")

-   But ... this changes those points.

-   And we are iterating over those exact points.

-   PROBLEM.

I was accessing the same thing in two different ways, which isn't allowed. And now that I'm a bit more comfortable with Rust, I can see *why* this is a great rule, and that my previous coding practices were perhaps a bit wild at times.

Realizing this, I did the "quick fix": first collect all edges we want to create. Then, in a new loop, just create all of those. That worked! But, as you'd expect, it was just a band-aid and couldn't solve further problems.

### The realization

I was approaching this project in a very Object-Oriented way, trying to put everything into these big objects (such as Point, Edge, etcetera). Even when I applied every fix, or hack, or change I knew ... new problems would always come up.

So I read some more of the documentation, watched some YouTube videos, tried some more things.

And then it clicked with me: I needed to *completely* stop thinking this way, and start **thinking in terms of data transformations.**

There's absolutely no need to aggregate all information for a point, and all its methods, inside a single big class.

A point in the level has several functionalities, each of which have *nothing to do with each other*.

-   It needs to know its position

-   Which entities are on it

-   Whether it is a special point (of some type)

-   Etcetera

But ... whether the point is special or not is *unrelated* to its position. So why even group them together? They are separate pieces of data, which should be handled and transformed separately.

That's how I ended up thinking. This is probably not the cleanest way to write it, but it helped me slowly grasp this concept over time. (And this isn't some big, long-term project.)

-   Instead of one Point struct, the game state now holds 4 separate arrays.

-   Points => the actual position of a point and whether it's active

-   PointEdges => the list of edges attached to it

-   PointEntities => the entities on it

-   PointSpecialties => the specialty of each point.

-   To get the information for point X, we just access the array we want *at position X*.

Why does this work?

-   These arrays are owned by the game state

-   Whenever I need their info, I can just directly access them by reference (array\[point_index\].do_something())

-   This way, they aren't owned by anything else and are never moved, making the compiler happy.

-   Additionally, because functionality is split into components, I don't need to do the "two-step process" of 1) grabbing the right point, then 2) grabbing the right function/subclass/part of it. I can grab what I want immediately, removing the need to have copies or references, which goes against the wishes of Rust.

### Taking data transformations further

The same can be done for Edges and Entities: just break them up into separate arrays, each holding one tiny component for them.

But we can go further. (Which was actually another breakthrough, although it sounds obvious in hindsight.)

Because this game takes place on a grid, there's a lot of coordinate conversions happening. For example:

-   Check if a point exists somewhere

-   Check if a move would be out of bounds

-   Convert point/edge indices (used in those arrays) to their real coordinates, and vice versa

In my first few tries, all of these were functions on the Board struct. Needed to check something? Call "Board.is_out_of_bounds(x,y)"

But this led to issues. Almost *every* function I called, needed to get a reference to the Board object, otherwise it couldn't call those helper functions. But they also needed a reference for other reasons, causing me to borrow that variable multiple times, making Rust unhappy.

The only solution would be to move *all* logic into the Board state, so it can just reference itself. But that's not really a clean coding practice and would lead to numerous issues down the road.

What to do? Well, don't give functions to a struct that *have nothing to do with that struct*. Instead, create something that *does what you want*, and instantiate that when needed.

Thus, the GridHelper was born.

It has a bunch of those helper functions, nothing more. Whenever I need to do calculations like these, I call the function I want on GridHelper.

This is, in my opinion, a prime example of **working with data transformations**. It's not like the GridHelper *is* something. It's not an object, or a class, or an entity or whatever. It doesn't represent something.

It's defined by what it *does*. And what it does, is transform data (e.g. coordinates of a point) into other data (e.g. a Boolean that says if it's out of bounds).

Programming it this way made Rust *very happy*. But, and this is the real benefit, it also made the code much cleaner and easier to write and use. *That's why I wanted to try Rust*. Within a few days, it has already led to endless insights into better coding practices and working more efficiently.

The one *downside* is that I need to pass a reference to the "state" to nearly everything. But it's a small price to pay for making code that actually works, is easy to use, and is safe.

(And I actually got the idea from the many, many game developers showcasing that this is how they do it. So maybe it feels wrong now, but I have some certainty I'm not going mad :p)

### Realizing the power of Commands

For this simulation, I needed to be able to "do" and "undo" anything on the board.

(Previously, I'd just copy the whole board state and alter that, but this led to memory issues and many stupid bugs. Storing 20 million unique boards in memory isn't great ... or possible. That's why I'm trying something else here.)

Thus I added a "Command" structure. Every time I change something, it's wrapped inside a command: Eat, Move, ChangePoints, Kill, etc.

Each command has two functions: the do() and the undo(). These do exactly what you think, and are often quite small and similar (just with some variables swapped, or a minus sign added).

At first, I was struggling to create a clean structure, because I tried to make the command *communicate* with modules on the entities.

Then I realized: the command **is** the module.

There's no reason to give Entities a "Move" component (or "Body" component) with functionality for moving. Because they are not the ones doing the moving, it's the *command* that does the moving. Again: it's about what things *do*, not what they *are*.

So I stripped the entity components of all that functionality, and moved it into the command. Then I did the same for all other commands, which means Entities are now just a bunch of structs holding their properties. Whenever they need to *do* something, I call the command with the right name.

And to make it even more powerful, a command can of course call other commands. The "Move" command, for example, does this:

-   Move entity from A to B

-   Then execute an **Encounter** on the edge it travels

The Encounter command does this:

-   Go through all active entities here

-   If we are bigger: call the **Eat** command on them

-   If they are bigger: call the **Eat** command on us

The Eat command:

-   Call a **PointChange** command (to get the points from the thing you've eaten)

-   Call a **Kill** command (to kill the other thing)

One line of code ("execute_move_command()") basically leads to ten tiny, simple commands. (The Kill command is literally one line. Same for PointChange.) Which are easily undone by going through them in reverse and calling "undo()" on them.

In other words: the "modularity" of my code comes from the commands, not from components on the entities/points/edges.

### Final notes on Rust

To be honest, many of the material available online for learning Rust is pretty terrible.

It's not that it's *incorrect* or *badly explained/presented*, it's that it has no *practical use* for a beginner.

I struggled the most with the overall structure of my Rust program. The global hierarchy, how to approach problems

But any examples online will just be tiny theoretical examples (in which they multiply two numbers, which of course won't lead to errors!), or these wildly complicated examples using ten keywords I didn't even know existed.

I think Rust could benefit from people just sharing:

-   This is a common problem

-   This is how you approach it, using only the Rust basics and minimal advanced concepts/keywords/code

-   And this is the final code I would write for it.

Because the hard part about programming languages is *not* learning the words to type and the basic concepts (such as loops and if-statements etc.). It's understanding how to even *begin* to approach problems from the philosophy of that language.

Anyway, with my new mindset of "data transformations everywhere!", I'm going to try and get the simulation working. (Just the basics: try all moves (do/undo), moving, eating bugs we encounter, return solution if it exists)

**Remark:** one of the first things I did was create a Debugger struct, with a function "pretty_print" that prints the whole game board to the terminal. (In a nice, visually clear way.) It was quite some work, but I've learnt this to be extremely useful. By printing each board created, I immediately see what's happening and what might be going wrong. Way more useful than printing text and numbers to the terminal.

## A working simulation

### The basics ("phase 1")

Alright, we have a working simulation.

-   Players can move

-   They can eat other bugs they encounter (which don't move yet, and are worth 1 point)

-   When they reach the objective, it's saved as a solution

-   After trying everything, I get back a large list with *all* possible solutions.

Firstly, now that it's actually functional (it ignores edges that don't exist, it stops going further when it's game over, etcetera), the number of states checked drops dramatically.

For a random 3x3 board, with 8 max moves, it checks roughly 10000-15000 states. That's not a lot and doable in a second.

Why do I return *all* solutions?

-   Because we do depth-first search, the first solution we get is not necessarily the most efficient. We only know the most efficient one when we have *all of them*.

-   I can use this information for more things.

A puzzle that has 1000 solutions ... is probably not great. A puzzle that has only 1 solution *might* be good, but it will often just be a trivial solution.

In a sense, we're aiming for the sweet spot: just enough solutions (of similar length) that it's a puzzle.

Additionally, this allows me to create different "difficulty levels" in the game. In previous puzzle games, I've noticed people getting a bit frustrated when they were just *one move short* of finding the perfect solution ... but because you had to find *the* best solution, they couldn't progress in the game.

With this system, I can "grade" players on a scale. Finding the best solution is 3 stars, finding the worst one is 1 star. (For example, not sure if I'm going to do this.)

It allows you to progress quite quickly (if you want, or get stuck trying to improve), you get results quickly (instead of staring at a screen, clueless), and it gives an incentive to go back to earlier puzzles and *improve* your score there.

### Another day, another game jam

I'd "kind of" planned to join another jam in the same month as making the original Windowsilk. When that day came, I decided to go through with that decision.

But under one condition: I'd make a *puzzle game* for that jam, allowing me to immediately test and practice my skills writing this Rust simulation. (Whatever happened, I'd be able to use the code and lessons learned from that game in this project afterwards.)

I ended up making **Windup Wizards** \<TO DO: Link>, a 3D puzzle game about winding up things ... and then activating them to do the actions you stored. It turned out quite well.

And taught me a lot about what I wanted to do for this game.

For example, I learnt ways to improve the simulation code and new ways to get better puzzles from the generator.

Most importantly, there were quite some disastrous bugs with my original implementation:

-   It would not try the *last* option in the list of all possible moves

-   Commands that added *other* commands, threw the order of the list into chaos, breaking the undo feature.

-   "Dying" in a puzzle resulted in *loads* of bugs, where things were suddenly gone and not reset, or the other way around, or they stayed dead when they shouldn't.

-   Not necessarily a bug, but something that needed to be fixed all the same: my original code was all in *one file*. This quickly grew 1000-2000 lines long. As such, I had to learn how to split things into files (and a clear hierarchy) using Rust.

In the end, I decided to spend the extra effort to *generalize* the code to any game logic.

This means that, whenever I create a new puzzle game from now on, I can just use the exact same simulation library, but add custom logic through code in extra files. This should speed up the "setup phase" for future puzzle projects immensely.

(For example, in this game a "move" is defined by a direction. In another puzzle game, a "move" might be a square you click, or both a direction *and* a distance, or whatever. The current system was not able to support this, which would make adapting it to future games a pain.)

I also learned that it's *crucial to follow identical logic between simulation and game*.

A few days before the jam deadline, I realized that my simulation was doing things in a *different order* than my game. And the problem hadn't surfaced until now.

Why? Because when I wrote that code, the order didn't matter, so I wrote it the way that was the easiest in the specific languages/software. But as the project grew, requirements changed, and these discrepancies became huge bugs that needed to be fixed.

Anyway, this game jam took 2 weeks of my time. And after doing 2 game jams in one month, I wanted to take a few days to rest.

Then and only then, was I ready to continue this project!
